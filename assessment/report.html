1. Executive Summary

The Rakamin AI Interview Platform conducts automated, real-time conversational technical interviews using Google Gemini Live, dynamically tracks skill coverage, synthesizes candidate portfolios, and compares candidate competency profiles against job vacancies (Fit/Gap analysis).

As a Product Engineer, our primary mandate is not simply writing code to specification, but owning the platform's real-world outcome: producing dependable, objective, and legally compliant talent evaluations that empower Indonesian hiring teams while protecting candidate livelihoods under UU PDP (Undang-Undang Perlindungan Data Pribadi).

This revamp resolves critical systemic failure modes across both services (api/ Rails and web/ React), introduces complete test harnesses for both applications, implements continuous integration (GitHub Actions), and polishes interaction states for hiring managers and assessors.

2. Deep Context & Domain Immersion (Step 2)

2.1 The Industry & Hiring in Indonesia

In Indonesia's tech sector, technical recruitment is throttled by two bottlenecks: massive applicant volume with high resume noise, and senior engineering leads spending 10-15 hours per week on screening interviews. AI interviews provide high leverage, but brittle evaluations or unhandled failure states quickly destroy recruiter confidence.

2.2 The Target Users & The Unchosen Candidate

  • Assessors & Hiring Managers: Need verbatim quote evidence, skill competency summaries, and human-in-the-loop override authority to adjust AI ratings when nuance requires it.
  • Recruiters & Talent Acquisition: Need seamless vacancy comparisons and exportable hiring recommendations.
  • Candidates & UU PDP (Law No. 27 of 2022): Candidates do not choose to be interviewed by AI. An unhandled error or false gap directly affects real careers. In compliance with UU PDP:
    • Data Minimization (Article 16): Personal identifiable information is never logged in plaintext or shared with LLMs beyond technical interview responses.
    • Right to Human Oversight (Article 37): Fully autonomous AI rejection is mitigated by human assessor override workflows with full auditability.

4. Revamp Strategy, Acceptance Criteria & Trade-offs (Step 4)

4.1 Self-Defined Acceptance Criteria

  • Resilient JSON Extraction: Regex-based object extraction strips markdown code fences and conversational preamble from LLM responses before parsing.
  • Graceful Degradation: If Gemini is unreachable, Fit/Gap engine generates deterministic rule-based narratives rather than crashing the request.
  • Transactional Integrity: Portfolio skill writes and session terminations are wrapped in atomic database transactions.
  • Human Override Reversibility: Assessor can remove an override via DELETE /api/v1/portfolio_skills/:id/override, restoring the AI baseline score without data loss.
  • Strict State Machine Invariants: Re-activation attempts on terminated sessions return existing records safely without modifying database state.

4.2 Trade-off Analysis: Option A vs Option B

Evaluation Dimension Option A: Resilient In-Process Parser & Fallback Engine (Chosen) Option B: External Strict Schema Microservice
Product Impact vs Cost High leverage, low cost. Delivers 100% resilience against LLM formatting quirks immediately within existing Rails architecture. High infrastructure cost and operational overhead with negligible end-user benefit.
Maintainability Superior. Pure Ruby/Rails patterns, easily understood, fully tested with RSpec unit specs. Fragmented repository and multi-repo deployment coordination overhead.
Failure Modes Graceful fallback to deterministic rule-based calculations if LLM times out. Additional point of failure in network pipeline.

5.2 Seeded Fault Test Proof

To verify our test suite detects real defects rather than executing shallow code, we ran a Seeded Fault Test:

  • Injected Fault: Weakened the probe count gate in Coverage::StateEngine.valid_transition? from probe_count < 2 to probe_count < 1.
  • Test Assertion Catch: RSpec immediately caught the regression: Coverage::StateEngine.valid_transition? blocks transition to partial if probe_count is less than 2: Failure/Error: expect(described_class.valid_transition?(...)).to be false
  • Resolution: Restored strict < 2 gate; all 30 tests returned to green.

5.3 AI Verification Moment

During implementation, an AI code assistant proposed using PortfolioSkill.where(portfolio_id: @portfolio.id).update_all(ai_level: ...).

Why It Was Wrong/Risky: update_all bypasses Active Record callbacks and validations, creating a critical vulnerability where invalid numbers (e.g., L0 or L9) could violate PostgreSQL check constraints (chk_portfolio_skills_ai_level).

Verification & Correction: We rejected update_all and implemented an explicit database transaction with level clamping (level = 1 if level < 1 || level > 5) and model validations.
